# Errand Agent

A chat agent that arranges home-service errands: plumber, electrician, AC servicing, cleaner, in
Bengaluru. It asks only for missing details, compares providers, and books, reschedules or cancels.
**Nothing happens without an exact confirmation from the user, and nothing is reported as done
until the provider confirms it.** Everything runs locally against a mock provider service.

The core idea is *the LLM proposes, code disposes*. The model understands requests and calls
read-only tools. Application code owns the state machine, the policy gate, approval cards, side
effects, verification and every outcome message.

## Quick start

Requires Python 3.12.

```bash
make setup                 # .venv + dependencies
cp .env.example .env       # then set GROQ_API_KEY, or LLM_PROVIDER=scripted to run without an LLM
make run                   # http://localhost:8000
make eval                  # all tests + scenarios, offline; writes evals/results.md and .csv
```

### Choosing the LLM

The agent talks to any OpenAI-compatible endpoint. Set these in `.env`:

| `LLM_PROVIDER` | Model | Needs |
|---|---|---|
| `groq` (default) | `openai/gpt-oss-120b` (alternative: `LLM_MODEL=qwen/qwen3.8-27b`) | `GROQ_API_KEY` |
| `ollama` | `qwen3:4b` (small enough for an 8 GB M1) | `brew install ollama && ollama pull qwen3:4b` |
| `openrouter` | set `LLM_MODEL` | `OPENROUTER_API_KEY` |
| `scripted` | the offline policy used by the evals | nothing |

`LLM_BASE_URL`, `LLM_MODEL` and `LLM_API_KEY` override the primary preset. `LLM_FALLBACK` is used when
a call fails: `groq:qwen/qwen3.8-27b` (the default in `.env.example`) is another Groq model with its
own rate-limit bucket, and `ollama` is local. A rate limit or outage falls back for that call only; a
bad key or unknown model switches for good. Every fallback is traced as `llm_fallback`.

**Groq free tier:** 8,000 tokens per minute and 200,000 per day, per model. A booking takes about
5–9 LLM calls of about 3,000 tokens each, so expect pauses while the client waits out 429s, and a few
dozen bookings a day. If the chosen provider has
no key, the web app runs the scripted policy and says so in the top bar. Costs in the trace are
estimates from the price table in `errand/config.py`.

## Using the web app

Chat is on the left, the live trace on the right. When the agent wants to act it shows a **card**
with the exact provider, slot and price, and a code. Click **Confirm**, or type `CONFIRM ABCD`.
Anything else ("yes", "ok") is not approval.

Try:
- `Find a plumber for my kitchen tap this week, mornings only, under ₹1,500.` (the area comes from memory)
- `Move my AC servicing to Saturday.`
- `Cancel my plumber booking.` (the first cancel call gets a 503; watch the same-key retry)
- `What do you remember about me?` · `My area is Koramangala now` · `Forget my parking`

Demo controls in the top bar:

| Control | What it does |
|---|---|
| **Scenario** + Reset | Wipe both databases and start a fresh session with a mock preset (below). "seed profile" loads 55 memories, a 200-message old session and past/upcoming bookings |
| **Provider cancels** | The provider cancels an upcoming booking. The watcher notices, tells you, and proposes a replacement card. Nothing is booked until you confirm |
| **+10 min** | Move the demo clock forward: cards and holds expire, UNVERIFIED re-checks run |
| **Crash next booking** | Kill the agent right after the next `book` call returns, before it records the result |
| **Restart agent** | New agent process over the same databases. Recovery asks the provider before doing anything |
| **Memory** | Inspect stored facts (used / waiting for confirmation / forgotten) and forget them |

Mock presets: `normal` (seeded random outcomes) · `price_drift` (the hold quotes more than the
search showed) · `timeout_booked` (book times out but did succeed) · `injection_first` (the provider
with the prompt-injection review ranks first) · `slot_conflict` (rescheduling the AC to Sat 14:00
conflicts).

The web app runs on a **demo clock**: real time, starting Tue 10 Nov 2026 09:00 IST. The mock's
bookings and availability are fixed in that week, so demos and tests behave the same on any date.

## Tests and evals

```bash
make test    # unit tests (mock contract, gate, approvals, executor, memory, tracer, web)
make eval    # everything, including tests/scenarios, and regenerates evals/results.md
```

- **Fully offline.** A socket guard fails any test that tries to reach the network. The scenarios
  drive the real orchestrator with `ReactivePolicy`, a scripted model that reads the same context a
  real LLM receives. Bad variants (`tests/bad_models.py`) call `book` themselves, lie about prices,
  invent IDs, claim success, obey injections and loop.
- **Invariants on every scenario** (`tests/invariants.py`), derived from the trace, the agent DB and
  the mock ledger:
  - I1: no side effect without a consumed approval and a write-ahead record
  - I2: at most one booking per errand
  - I3: no unsupported outcome claims
  - I4: every run ends with a message
  - I5: no forgotten or unconfirmed value in any context
  - I6: no approval or memory sourced from tool output
  - I7: no payload mismatch; side effects only through the gate
- **Deterministic**: frozen clock, seeded mock. The table is identical across runs.

## How it is built

```
browser ── FastAPI (errand/web) ── Runtime ── Agent (orchestrator) ──► LLM client (OpenAI-compatible)
              │  SSE: trace + notifications       │  context builder ─ memory
              │                                   │  gate ─ approvals ─ executor ─► mock provider
              └── watcher loop ───────────────────┘  tracer ─► traces/*.jsonl      (separate SQLite DB)
```

| Path | Role |
|---|---|
| `errand/agent/orchestrator.py` | The loop: route code / message, build context, call the LLM, run tools through the gate |
| `errand/agent/state.py` | Errand states, legal transitions, tools allowed per state |
| `errand/agent/gate.py` | Policy checks for every LLM tool call and every executor side effect |
| `errand/agent/approvals.py` | Draft → hash → card → code; atomic consume into a write-ahead execution |
| `errand/agent/executor.py` | Book / cancel / reschedule with idempotency keys, verification, retries, re-holds |
| `errand/agent/recovery.py`, `watcher.py` | Restart recovery; provider cancellations, UNVERIFIED follow-up, approval expiry |
| `errand/agent/memory.py`, `context.py` | Memory statuses, provenance, forgetting; budgeted, logged context |
| `errand/agent/sanitize.py`, `claim_guard.py`, `templates.py` | Untrusted tool output; blocking false claims; code-owned outcome messages |
| `errand/agent/llm/` | OpenAI-compatible client with fallback; the scripted offline policy |
| `errand/mocks/` | Provider catalog (28 providers, injection review), scenario presets, the mock service |
| `errand/tracing/` | JSONL tracer with PII masking and cost estimates |
| `errand/web/` | FastAPI app, runtime with demo controls, static UI |
| `tests/` | `harness.py` (Sim, SimUser), `invariants.py`, `bad_models.py`, eval-table plugin in `conftest.py` |

Data lives in `data/` (agent and mock SQLite DBs, recreated on Reset) and traces in `traces/`.
Both are git-ignored except the committed demo trace.

## Known limitations

- The offline policy understands only the phrasings the scenarios use. Open-ended language goes
  through the real LLM.
- "Book the same electrician as last time" is left to the real LLM (via `list_bookings`); there's no
  offline scenario for it yet.
- One demo user (`u1`) and one session at a time in the web app; no authentication.
- LLM prices are list-price estimates.
